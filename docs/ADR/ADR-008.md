# ADR-008: Core Contracts Module

## Status

Proposed

## Date

2026-08-08

## Context

The platform requires standardized interfaces for engines and data providers. These interfaces establish the "plugs" for the decision engine ecosystem, enabling the Orchestrator to coordinate execution and data retrieval without coupling to specific implementations.

Currently, `core/types` defines the data contracts (what), `core/results` defines the output structure, but no module defines the behavior contracts (how engines and providers expose their capabilities).

ARCHITECTURE.md §7.1 defines the Provider Interface Contract with three operations: `fetch(parameters)`, `validate(credentials)`, `transform(raw)`. ARCHITECTURE.md §9 defines the Result Object that every engine must return.

The Core Contracts module must bridge these requirements, providing stable interfaces that engines implement and the Orchestrator consumes.

## Decision

Create the Core Contracts module as a standalone immutable contract layer in `core/contracts/`.

This module defines two primary contracts:

1. **IEngine<TRequest, TData>** – The contract for decision engines.
2. **IDataProvider<TParams, TData>** – The contract for data providers.

Both contracts use generic parameters to support diverse implementations while maintaining type safety.

## Core Contracts Responsibility

- Define the interface for all decision engines.
- Define the interface for all data providers.
- Remain implementation-agnostic.
- Contain no business logic.
- Depend only on `core/types` and `core/results`.
- Serve as the authoritative source for engine and provider contracts.

## IEngine Contract

The `IEngine` contract defines how engines expose their core execution capability.

```typescript
interface IEngine<TRequest, TData> {
  execute(request: TRequest): Promise<Result<TData>>;
}
TRequest – The type of the request accepted by the engine.

TData – The type of the data returned in the Result object.

Engines are expected to be stateless and deterministic. The execute method encapsulates the entire engine operation.

IDataProvider Contract
The IDataProvider contract defines how providers expose data retrieval.

typescript
interface IDataProvider<TParams, TData> {
  fetch(params: TParams): Promise<TData>;
  validate(credentials: unknown): Promise<boolean>;
  transform(raw: unknown): TData;
}
TParams – The type of parameters required for the data fetch.

TData – The type of data returned by the provider.

Providers are expected to handle their own authentication, rate limiting, and error handling. They must transform external data into the platform's canonical types.

The validate and transform operations align with ARCHITECTURE.md §7.1.

Relationship with Result<TData>
IEngine.execute() returns Promise<Result<TData>>, where Result<TData> is the standardized Result Object from core/results.

This ensures every engine output conforms to the mandatory structure defined in ADR-007.

Relationship with Frozen Core Types
Core Types v1.0 is frozen and must not be modified.

Core Contracts may import and use Core Types where appropriate (e.g., ID, Timestamp, Metadata).

No Core Types file may be modified.

Dependency Direction
Source	May Depend On
core/contracts/*.ts	core/types, core/results only
core/contracts/index.ts	All other files in core/contracts/
Core Contracts must remain isolated from engines, platform, products, and other modules.

Immutability Expectations
All interfaces must be immutable by design.

Properties must be readonly where applicable.

Methods are not subject to readonly.

No-Business-Logic Rule
Core Contracts contain no business logic.

No validation logic.

No transformation logic.

No calculations.

No behavior.

Rejected Alternatives
Contracts as part of Core Types
Rejected because:

Core Types v1.0 is frozen. Adding behavior contracts would violate the freeze policy and mix data contracts with behavior contracts.

No generic parameters (using unknown)
Rejected because:

Using unknown would sacrifice type safety and require casting in every implementation. The project's commitment to banking-grade clarity and maintainability favors explicit generic parameters.

Separate contracts for each engine type
Rejected because:

A single generic contract is sufficient. Different engine types can be distinguished by their TRequest and TData types.

Full lifecycle methods (validate, status, health)
Rejected because:

These are operational concerns, not core architectural contracts. They belong in implementation layers, not in Core Contracts.

Consequences
Positive
Clear, stable contracts for engines and providers.

Type-safe generic parameters.

Consistent dependency direction.

Enables independent engine development.

Supports future engine addition without architecture changes.

Negative
All engines must implement the same contract.

Generic parameters require discipline to use correctly.

Slight learning curve for engine developers.

Future Implications
The Orchestrator will depend on IEngine and IDataProvider.

New engines must implement IEngine<TRequest, TData>.

New data providers must implement IDataProvider<TParams, TData>.

These contracts are frozen once approved.
